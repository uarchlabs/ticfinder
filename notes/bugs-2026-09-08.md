# Findings from running the new version against two blog documents

Date: 2026-09-08
Version: 99d9a3e "findings and bkms for use"
`make regress` passes all six sections; none of these is caught by it.

## 1. Masking can manufacture a finding (false positive)

Blanking inline code preserves offsets but changes the parse, so a
finding can exist in the masked text that does not exist in the source.
Documented behaviour is that the quoted text misleads; this is stronger.

Repro, identical prose, backticks the only difference:

    A: aging ran with `tage_enable_aging`
       and `ittage_enable_aging` held at zero in every test
       -> TRICOLON [3-part VERB, list-like]  fe30d3

    B: aging ran with tage_enable_aging
       and ittage_enable_aging held at zero in every test
       -> no finding

Masking leaves "aging ran with __ and __ held at zero". The noun
coordination is gone and the residue parses as coordinated verbs. Seen
in the wild as fe30d3 in BLOG_bpu_14_directed_validation.md L73, which
is why that document is deliberately left at 1 unwaived finding.

Suggested test: any sentence whose only coordination is between two
inline-code spans must not report TRICOLON.

## 2. An element outside the list joins the conjunct set

Correction to a first reading: this is not about numerals. Using the
sentence exactly as it appears in the article,

    Three of the specification errors were found by the implementation
    assistant reporting a discrepancy it was not asked to look for: the
    allocation write-data field order, the pred_strong carryover, and
    the stored final-target field.
    -> TRICOLON [4-part NUM, enumeration]

    Several of the ... (same sentence otherwise)
    -> TRICOLON [4-part ADJ, enumeration]

The list has three members in both. The count is 4 either way, and only
the head POS changes, following whatever word leads the sentence. One
element from outside the list is entering the conjunct set.

Shortening the sentence stops it reproducing, which is worth knowing
before writing a test for it.

Effect is on the label, not on whether the finding fires, so it is
cosmetic until the label drives the confidence -- which it now does,
since `figure` reports at medium and the other two at low.

## 3. A verb coordination merges with a following appositive list

    Both extended checks failed before the fix and passed after.
    -> no finding (correct, 2-part)

    Both extended checks failed before the fix and passed after, with
    the failing values showing the exact corruption: expected c000,
    actual e000, and expected c000, actual b000.
    -> TRICOLON [4-part VERB, list-like]

Two coordinated verbs plus a two-pair appositive list are reported as
one 4-part VERB coordination. Neither part is a tricolon on its own.

This is the same defect as #2, seen from the other side: an element
outside the appositive list joins its conjunct set, the count comes back
one too high, and the head POS follows the outside element. In #2 that
element is the sentence's lead nominal; here it is the verb pair.
`follow_appos` is new in this version and is the first place to look.

## Not a defect: the widened TRICOLON

Reporting every coordination of three or more re-opened
BLOG_bpu_14_directed_validation.md from 0 findings to 19 with no change
to the document. That is the intended trade and the labels carry it:
of the 19, not one came back `figure`. Every one was `list-like` or
`enumeration`, which is the tool correctly saying these are ordinary
lists in a technical document. 18 were waived on that basis.

Worth noting in the README: a detector change re-opens documents that
were clean, so a waiver file is only clean against the version that
wrote it.

# Follow-up, same day, after the fix

The three defects above are fixed and verified. Masking now leaves the
identifier in place and blanks only the backticks, which is what removed
the phantom at root. Note that this changes the word count of an
unedited document (BLOG_bpu_14 went 5059 -> 5179), so per-1000 rates are
not comparable across the two versions.

## 4. Bare identifiers score as `figure`

The mirror image of #2 and #3. Two findings in BLOG_bpu_14 now come back
`figure`, the only label reported at medium confidence, and both are
ordinary lists:

    79f444  [3-part PROPN, figure]  tbl_hit_p1, tbl_cntrl_bits_p1 and
                                    tbl_pred_tgt_p1
    61bfec  [3-part PROPN, figure]  (FTB, SC and RAS

Every enumeration signal in the scorer is defined over English noun
phrases: determiners on the items, premodifiers, a cue word in the
lead-in, uneven member widths. A list of bare signal or unit names has
none of them, scores 0, and falls through to `figure`.

So in technical prose the most confidently reported finding in a
document can be a plain list of identifiers. The failure direction
matters: #2 and #3 pushed real figures down toward `enumeration`; this
pushes ordinary lists up toward `figure`.

Possible signal: members that are PROPN, or that were inline code in the
source, or that match an identifier shape (underscore, digit suffix,
mixed case). Any of those is evidence of a catalogue rather than a
rhetorical triad.

Repro: any sentence coordinating three short identifiers.

    The block drives tbl_hit_p1, tbl_cntrl_bits_p1 and tbl_pred_tgt_p1.
    -> TRICOLON [3-part PROPN, figure]     want: enumeration or list-like

## 5. Duplicate id when a sentence contains the same match twice

Benign, noted for completeness. A sentence with two identical matches
reports one fingerprint twice, because the hash covers the construction,
pattern, matched text and containing sentence, all of which are equal:

    A paragraph explaining that `rather than` is ordinary English
    contains the phrase `rather than`.
    -> 6bece7 reported at both offsets

Waiving the id covers both, so there is nothing to fix unless the
duplicate line in the report is itself unwanted.
