## Hypothesis
Phase 1. The 4-space indented-code rule is markdown syntax. In plain text,
indentation is layout, so the rule blanks the author's prose (about 530
lines in 6 spec files, TF-002). Applying it only to markdown files, and
letting the code masker judge indented lines in plain text, restores that
prose without letting code back in. The other two fixes (trailing
comments, `name : value.call(arg)` DSL lines) reduce the under-masking
found in about 10 of 36 spec files. The blogs are markdown, so harvest
should not change. The phase 1 hypothesis fails if harvest changes, if
the specs' code-masked share falls when the indented-code rule is
narrowed (code leaking back in), or if spot-checks show new over-masking.

Phase 2. Accepted `TRICOLON` findings are mostly lists of referents
(identifiers, named components, defined terms), and rewritten ones are
mostly lists of qualities or abstractions ("simpler, faster, and easier
to debug"). A per-member referent score separates them better than the
current enumeration score, which roadmap section 4 showed does not
discriminate (`list-like` holds 52 of 84 accepted and 13 of 17
rewritten). The phase 2 hypothesis fails if the referent score does not
separate accepted from rewritten findings in `eval/labels.jsonl`. That
is a null result: record it and keep the code out (CLAUDE.md).

TF-002 specs aggregates (36 text files, `.docx` skipped): 97,901 words

Code-masked share per file: min 0.0, median 0.3, max 33.5. Markdown-masked

The `TRICOLON` detector reports every coordination of three or more and
labels it `figure`, `list-like` or `enumeration` from an enumeration
score. The label is in the finding's label text and sets confidence.
Fingerprints hash construction, pattern, matched text and sentence; the
subtype label is not part of the hash.

## Binding Previous Decisions
- Masking preserves character offsets and newlines: blank in place,
  never delete.
- Inline code keeps its text; only the backticks are blanked. Lines that
  contain inline code are never code-masked (TF-002).
- The fingerprint formula is unchanged by this task.
- Waiver ids hash the full sentence (TF-001).
- Thresholds are named module-level constants with a comment saying how
  they were set (TF-002).
- `--no-code-mask` keeps working and keeps its meaning.
- Single dependency-light script; no new third-party dependencies.

## Specific Requirements

### Phase 1: masking fixes

1. **Confirm the baseline.** Run `make regress` and harvest. Save the
   harvest output and `labels.jsonl` to the scratchpad. Record the specs
   aggregates with the TF-002 method and confirm they match the
   Background.
2. **Indented code in plain text, test rows first.** Add `masking` rows:
   indented prose in a plain-text file must be kept; indented code in a
   plain-text file must be blanked (by the code masker); indented code in
   a markdown file must still be blanked (by the markdown rule). Then
   change `mask_markdown` so the indented-code rule applies only to
   markdown input. Decide how the file type reaches `mask_markdown` (a
   parameter set by `analyse()` from the file suffix is the obvious way)
   and state the choice. `harvest.py` calls `mask_markdown` directly;
   keep its behaviour for `.md` files.
3. **Trailing comments, test rows first.** Positive rows: a code line
   ending in a `//` comment and one ending in a `#` comment must be
   blanked whole. Negative rows: a prose sentence with `TD #104` in it, a
   line with a URL (`https://...`), and a markdown heading must be kept.
   Score the part before the comment marker; blank the whole line when
   that part is code.
4. **DSL lines, test rows first.** Positive rows: `name : value.call(arg)`
   and `name : a.b(c).d(e)` forms must be blanked. Negative rows: a
   glossary line of the form `Term: a description in ordinary words`, and
   `Note: see the section above.`, must be kept. Write invented examples;
   do not copy lines from the specs.
5. **Measure phase 1.**
   - `make regress` passes.
   - Harvest after, compared with step 1. Expected: identical. If any
     finding changes, list it with its label and stop and report.
   - Per-file markdown and code shares for the 7 harvest blogs, notes/,
     README.md: expected unchanged.
   - Specs aggregates after: words raw, after markdown masking, after
     code masking; distribution of markdown-, code- and total-masked
     share (min, median, max, count over 40%).
   - Spot-check again as in TF-002: a random sample of blanked lines and
     of kept lines with code signals. Report the counts of code and
     non-code in each sample and the failure kinds in general terms. Do
     not quote the specs.
   - Stale waiver count per waiver file in `$PACINO/waivers` and
     `waivers/` caused by phase 1.
6. **Stop.** Record phase 1 results in roadmap section 10 (TF-003
   results), summarize the files changed, the `make regress` result and
   the measurements, and suggest a commit message. Wait for the user to
   commit before starting phase 2.

### Phase 2: TRICOLON licensing

7. **Confirm the phase 2 baseline.** Run harvest after the phase 1
   commit and save it as the phase 2 before-measurement.
8. **Offline separation test first.** Before changing `tricolon()`,
   compute a referent score for every `TRICOLON` row in
   `eval/labels.jsonl` (accepted, rewritten, deleted). Score each list
   member as a referent when it is identifier-shaped (underscore, digit
   suffix, mixed case, inline code in the source), a proper noun, a
   number or quantity, or a noun phrase that recurs as the same phrase
   elsewhere in the document. Score it as a quality when it is an
   adjective, an adverb, or an abstract noun that appears once. Report
   the distribution of the score for accepted and for rewritten
   findings, and the precision and recall at each cut. Compare with the
   current `figure`/`list-like`/`enumeration` labels on the same rows.
   - If the score does not separate the classes, record a null result in
     the roadmap and `notes/`, keep the code out, and stop.
9. **Design choice, stop and ask.** If the score separates the classes,
   present the options to the user before coding:
   - (a) a new subtype label (for example `catalog`) with low confidence,
     same pattern: no waiver goes stale, but users cannot mute it with
     `--off` on its own;
   - (b) a new pattern under `TRICOLON` (for example `tricolon_catalog`):
     mutable on its own (CLAUDE.md: anything a user would want to mute
     separately needs its own id or pattern), but every existing waiver
     for a finding that moves becomes stale, because the fingerprint
     hashes the pattern. Count those waivers per file before asking, and
     say what a migration would need.
   Do not suppress findings outright; every construction is legitimate
   somewhere.
10. **Implement, test rows first.** Add `detectors` rows: lists of
    identifiers, of named components and of defined terms that must get
    the referent label; lists of qualities ("simpler, faster, and easier
    to debug") that must keep `figure`; and a mixed list. The threshold
    is a named constant with a comment saying it came from step 8.
11. **Harvest by subtype.** Add a `--by-subtype` option to `harvest.py`
    that groups the summary by construction, pattern and subtype (from
    the label text). Rows without a subtype group as `-`.
12. **Measure phase 2.**
    - `make regress` passes.
    - Harvest after, by pattern and by subtype: rewritten, deleted,
      accepted and prec* for each. The main measure is how many of the
      84 accepted `TRICOLON` findings move to the referent label, and how
      many of the 19 rewritten ones do. Report both; 19 rewritten labels
      are too few for a tight precision figure, so give the counts.
    - List the rewritten findings that moved to the referent label, with
      matched text and sentence, so the user can judge them.
    - Stale waiver count per waiver file, as in phase 1. Zero is expected
      for option (a).
13. **Record results** in roadmap section 10, including any null result,
    and fill in the RESULTS block of this file.
