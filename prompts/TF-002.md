## Hypothesis
Code that is not fenced or backticked (identifier runs, port and
register listings, expressions, signal tables written as prose lines)
is parsed as English and produces false positives, mostly in TRICOLON
(comma-separated identifiers read as a list or a `figure`). Masking it
removes more accepted findings than rewritten ones, so TRICOLON prec*
rises. In the specs corpus, code-like text is a large share of each
file, and without this masker it would inflate the human base rates
that roadmap steps 4 and 5 need.

The hypothesis fails if the masker removes rewritten findings at the
same rate as accepted ones, or removes almost nothing from the blogs.
Either outcome is reported as a null result for the blogs (CLAUDE.md
"Report null results"). The masker may still be needed for the specs.

The `masked_pct` bug, found at the end of TF-001: `analyse()` computes
`1 - len(masked.strip()) / len(raw.strip())`. Masking blanks text in
place without changing its length, so the ratio moves only when the
masked text is at the start or end of the file. Measured on non-space
characters, README.md is 30% masked and reports 0.0; BLOG_bpu_14 is 22%
and reports 0.5; BLOG_bpu_16 is 29% and reports 0.0. The warning at
`masked_pct >= 40` can never fire.

## Binding Previous Decisions
- Masking preserves character offsets: blank in place, never delete.
  Newlines stay.
- Inline code keeps its text and only the backticks are blanked
  (`unquote` in `mask_markdown`). The new masker does not change this.
- The fingerprint formula is unchanged by this task. Masking can still
  change sentence boundaries, which changes a finding's context and so
  its id. Report how many existing waivers go stale; do not prune or
  migrate them.
- Waiver ids hash the full sentence (TF-001). `--migrate-waivers` is
  only for the old 240-character ids and does not apply here.
- `never` is not an em-dash negator (TF-001).
- Single dependency-light script; no new third-party dependencies.
